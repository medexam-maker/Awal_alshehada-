# PD-004: Exam Finalization Security and Credential Invalidation

- **Status**: DRAFT / PENDING LEADERSHIP APPROVAL
- **Date**: 2026-10-15
- **Scope**: Exam Engine / Security Boundary / Invalidation Recovery
- **Contracts Baseline**: C1–C9 FROZEN at v1.1.0

---

## 1. Scope & Objective
This document outlines the architectural boundaries, threat model, and security constraints governing exam finalization (`POST /api/exam/finish`) when credential invalidation events occur during an active, offline examination attempt.

It formalizes the separation of exam finalization security from standard refresh token lifecycle decisions (PD-003).

---

## 2. Threat Model & Operational Context
1. **The Zero-Request Invariant (PD-002, C4 §20–§21, C5 §62 Rule 4, C6 §19)**:
   - During active examination answering (which may last 2 to 3 hours in Simulator mode), the client operates strictly offline and performs zero API requests.
2. **Concurrent Credential Invalidation (C7 §7, PD-003 D4)**:
   - While the student is answering questions offline, a security event may occur on another device or administratively (e.g., password change, administrative account suspension, or verified session compromise).
   - This event increments `users.token_version` and revokes active refresh tokens.
3. **The Finalization Conflict**:
   - When the student completes the exam and reconnects to submit answers (`POST /api/exam/finish`), the access token is rejected (`AUTH_REQUIRED` due to `token_version` mismatch).
   - An insecure workaround (such as allowing any attempt with `attempt.status = 'in_progress'` to bypass `requireAuth` or ignore `token_version`) constitutes an unacceptable authentication bypass. An attacker could exploit such an exception to tamper with or finalize unauthorized attempts.
   - Conversely, abruptly rejecting finalization without a recovery mechanism causes permanent loss of the student's legitimate examination effort and answers.

---

## 3. Mandatory Security Constraints
1. **No Token-Version Bypass**:
   - `requireAuth` and `POST /api/exam/finish` MUST NOT exempt requests based on `attempt.status = 'in_progress'`.
   - Every finalization request must establish verified server-authoritative identity and authorization.
2. **No Unauthenticated Finalization**:
   - Mock identity, client-asserted identity headers, or unauthenticated FINISH submissions are strictly prohibited.
3. **Immutable Local Answer Preservation**:
   - In accordance with PD-002, authentication failure at submission MUST NOT clear or destroy the locally recorded answers.
4. **Attempt Expiration Timer Authority**:
   - Exam timer validation remains server-authoritative. Authentication recovery does not suspend or extend the server timer or the 120-second Simulator grace window.

---

## 4. Unresolved Decisions & Architectural Alternatives

### Alternative A — Client-Side Re-Authentication Challenge (Recommended for Evaluation)
- When `POST /api/exam/finish` returns HTTP 401 with `code: 'AUTH_REQUIRED'`, the client UI presents an immediate modal credential challenge ("Re-authenticate to submit your exam").
- The student enters their new password. The client calls `POST /api/auth/login` to obtain an updated access token bearing the new `tokenVersion`.
- The client then immediately dispatches `POST /api/exam/finish` with the new token.
- *Pros*: Zero changes to frozen backend contracts C4/C5/C7; zero security bypass; strictly adheres to server-authoritative identity.
- *Cons*: Requires student to know their updated credentials at submission time.

### Alternative B — Signed Exam Finalization Ticket (EFT)
- At exam start (`POST /api/exam/start`), the server issues an asymmetric/HMAC-signed single-use ticket bound strictly to `(attemptId, userId, expiresAt)`.
- The ticket can only be consumed once specifically at `POST /api/exam/finish`.
- *Pros*: Decouples exam submission from general account session lifetime.
- *Cons*: Introduces a new credential type not specified in C4/C7; requires formal contract amendment to C4 and C7.

---

## 5. Governance Status
- Neither Alternative A nor Alternative B is approved for implementation in Phase 2.4.
- Any implementation requires a formal resolution by the Project Owner.
- C1–C9 remain FROZEN at v1.1.0 without modification.
